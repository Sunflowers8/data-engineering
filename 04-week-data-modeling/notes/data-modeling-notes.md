# Week 4 — Data Modeling Notes

## 1. What is Data Modeling?

Data modeling defines how data is structured, related, and stored.

In analytics systems, dimensional modeling organizes data so that analytical queries are easier to understand and execute.

A common structure is:

```text
Dimensions → Fact Table ← Dimensions
```

---

## 2. Fact Tables

A fact table stores measurable business events.

Examples:

- Taxi trip
- Order
- Order item
- Payment
- Sale

Our NYC Taxi fact table is:

```text
fact_taxi_trip
```

### Grain

The grain defines exactly what one row represents.

NYC Taxi grain:

> One row in `fact_taxi_trip` represents one NYC taxi trip.

E-commerce example:

> One row in `fact_order_items` represents one product line item within one order.

The grain should be defined before choosing measures and dimensions.

---

## 3. Dimensions

Dimensions describe the context surrounding a fact.

NYC Taxi dimensions:

```text
dim_date
dim_location
dim_vendor
dim_payment_type
```

Examples of descriptive attributes:

```text
dim_location
------------
borough
zone
service_zone
```

Dimensions answer questions such as:

- Where?
- When?
- Who?
- What type?
- Which category?

---

## 4. Measures

Measures are numeric values stored in fact tables for analysis.

NYC Taxi measures include:

```text
passenger_count
trip_distance
fare_amount
tip_amount
tolls_amount
total_amount
trip_duration_minutes
```

E-commerce measures include:

```text
quantity
unit_price
revenue
```

Identifiers such as `order_id`, `customer_id`, and `product_id` are not measures.

---

## 5. Additive Measures

An additive measure can be meaningfully summed across dimensions.

Examples:

```text
revenue
quantity
fare_amount
```

Example:

```text
Revenue Product A = 1000
Revenue Product B = 500

Total revenue = 1500
```

---

## 6. Semi-Additive Measures

A semi-additive measure can be summed across some dimensions but not all dimensions.

Example:

```text
daily account balance
```

Balances from different accounts on the same date may be summed.

However, adding the same account balance across multiple dates usually does not represent a meaningful balance.

Example:

```text
Oct 1 = 10,000
Oct 2 = 12,000
Oct 3 = 11,000
```

The account balance is not:

```text
33,000
```

This is why account balance is semi-additive across time.

---

## 7. Business Keys

A business key comes from the source/business system.

Examples:

```text
customer_id
product_id
location_id
vendor_id
payment_type_id
```

It identifies a business entity in the source system.

---

## 8. Surrogate Keys

A surrogate key is generated by the warehouse.

Examples:

```text
customer_key
product_key
location_key
vendor_key
payment_type_key
```

Example:

```text
vendor_key = 1
vendor_id  = 1
```

The values may sometimes look identical, but they represent different concepts.

A surrogate key is controlled by the warehouse.

---

## 9. Primary Keys

A primary key uniquely identifies a row.

Example:

```sql
customer_key INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

In:

```text
dim_customer
```

`customer_key` is the primary key.

---

## 10. Foreign Keys

A foreign key references the primary key of another table.

Example:

```text
dim_customer.customer_key
        ↑
        |
fact_orders.customer_key
```

In this example:

```text
dim_customer.customer_key = Primary Key
fact_orders.customer_key  = Foreign Key
```

---

## 11. Normalization

Normalization organizes operational data to reduce unnecessary duplication and update problems.

---

## 12. First Normal Form — 1NF

1NF requires fields to contain atomic values.

Bad:

```text
customer_id | phone_numbers
101         | 9800000000,9811111111
```

One field contains multiple phone numbers.

Better:

```text
customer_id | phone_number
101         | 9800000000
101         | 9811111111
```

Memory:

> 1NF = one value per field.

---

## 13. Second Normal Form — 2NF

2NF removes partial dependencies when a composite key exists.

Example composite key:

```text
(order_id, product_id)
```

If:

```text
product_name
```

depends only on `product_id`, it does not depend on the whole composite key.

This is a partial dependency.

Memory:

> 2NF = depend on the whole key.

---

## 14. Third Normal Form — 3NF

3NF removes transitive dependencies.

Example:

```text
employee_id → department_id
department_id → department_name
```

`department_name` depends on another non-key attribute instead of directly on the primary key.

A better design separates departments into another table.

Memory:

> 3NF = depend on nothing but the key.

---

## 15. Star Schema

A star schema contains a central fact table connected directly to dimensions.

Example:

```text
                 dim_date
                    |
dim_vendor ── fact_taxi_trip ── dim_payment_type
                    |
               dim_location
```

Advantages:

- Simple analytical queries
- Fewer joins
- Easy for analysts to understand
- Useful for BI and reporting

---

## 16. Snowflake Schema

A snowflake schema normalizes dimensions into additional related tables.

Example:

```text
fact_order_items
       |
   dim_product
       |
  dim_category
       |
dim_department
```

Compared with a star schema, a snowflake schema can reduce some duplication but normally requires more joins.

---

## 17. Star vs Snowflake

For analytics and dashboards, a star schema is often preferred when simplicity and fewer joins are important.

```text
Star
→ More denormalized dimensions
→ Fewer joins
→ Simpler analytics

Snowflake
→ More normalized dimensions
→ More joins
→ More structural separation
```

---

## 18. Role-Playing Dimensions

The same dimension can be used in different roles.

NYC Taxi uses `dim_location` twice:

```text
pickup_location_key  → dim_location
dropoff_location_key → dim_location
```

The same dimension describes both pickup and dropoff locations.

This is a role-playing dimension.

---

## 19. Conformed Dimensions

A conformed dimension is shared consistently across multiple business processes/fact tables.

Example:

```text
fact_orders   ──→ dim_customer
fact_returns  ──→ dim_customer
fact_payments ──→ dim_customer
```

Because all processes use the same customer definition, `dim_customer` is a conformed dimension.

---

## 20. Bus Matrix

A bus matrix shows which dimensions are used by different business processes.

Example:

| Business Process | Customer | Product | Date |
|---|---|---|---|
| Orders | Yes | Yes | Yes |
| Returns | Yes | Yes | Yes |
| Payments | Yes | No | Yes |

This helps identify reusable/conformed dimensions.

---

## 21. Event Modeling

An event represents something that happened at a specific time.

Examples:

```text
Order placed
Payment completed
Order shipped
Order delivered
Product returned
```

Example:

```text
event_id | order_id | event_type | event_time
1        | 1001     | PLACED     | 10:00
2        | 1001     | PAID       | 10:05
3        | 1001     | SHIPPED    | 09:00 next day
```

Event data can be used to analyze process duration and behavior over time.

---

## 22. Slowly Changing Dimensions

Dimension attributes can change over time.

Example:

```text
Customer city:
Kathmandu → Pokhara
```

The warehouse must decide how the change should be handled.

---

## 23. SCD Type 1

SCD Type 1 overwrites the old value.

```text
Before:
Kathmandu

After:
Pokhara
```

The historical Kathmandu value is lost.

Memory:

> SCD1 = overwrite history.

---

## 24. SCD Type 2

SCD Type 2 preserves history by creating a new dimension version.

Example:

```text
customer_key | customer_id | city       | effective_from | effective_to | is_current
7            | 205         | Kathmandu  | 2026-01-01     | 2026-08-14   | false
8            | 205         | Pokhara    | 2026-08-15     | NULL         | true
```

The source business identifier remains:

```text
customer_id = 205
```

but each historical version receives a different surrogate key.

Memory:

> SCD2 = preserve history.

---

## 25. SCD2 Fact Relationships

Historical facts should reference the dimension version valid when the event happened.

Example:

```text
Old order → customer_key 7
New order → customer_key 8
```

This is why facts reference the surrogate `customer_key`, not only the source `customer_id`.

---

## 26. SCD2 Date Lookup

Example:

```sql
JOIN dim_customer dc
    ON o.customer_id = dc.customer_id
   AND o.order_date >= dc.effective_from
   AND (
       dc.effective_to IS NULL
       OR o.order_date <= dc.effective_to
   )
```

This matches an order to the customer version that was valid on the order date.

---

## 27. Date Dimension

A date dimension provides reusable calendar attributes.

Our structure:

```text
dim_date
--------
date_key
full_date
day
day_name
month
month_name
quarter
year
is_weekend
```

Example:

```text
full_date = 2026-10-06
date_key  = 20261006
```

The key follows:

```text
YYYYMMDD
```

---

## 28. Generating Dates in PostgreSQL

PostgreSQL `generate_series()` can generate calendar dates.

Example:

```sql
SELECT generate_series(
    '2026-01-01'::date,
    '2026-01-31'::date,
    INTERVAL '1 day'
)::date;
```

January 2026 generated 31 date records.

---

## 29. Dimension Lookups

Source data usually contains business keys.

Example:

```text
taxi_trips.vendor_id
```

The warehouse fact table needs the surrogate key:

```text
dim_vendor.vendor_key
```

Lookup:

```sql
JOIN dim_vendor v
    ON t.vendor_id = v.vendor_id
```

Rule:

> JOIN using business keys and retrieve surrogate keys.

---

## 30. Multiple Roles from One Dimension

Pickup:

```sql
JOIN dim_location pickup
    ON t.pu_location_id = pickup.location_id
```

Dropoff:

```sql
JOIN dim_location dropoff
    ON t.do_location_id = dropoff.location_id
```

Aliases allow the same dimension table to perform multiple roles.

---

## 31. Missing Dimension Matches

An `INNER JOIN` removes source rows that do not have a matching dimension record.

During the NYC Taxi project:

```text
payment_type = 0
```

existed in the source but was initially missing from `dim_payment_type`.

The missing value was added as:

```text
0 = Flex Fare
```

After the correction, the dimension contained seven payment types.

---

## 32. Data Quality Checks Before Fact Loading

Before loading the fact table, dimension coverage was checked using `LEFT JOIN`.

The checks compared:

```text
total source rows
pickup location matches
dropoff location matches
vendor matches
payment matches
date matches
```

The goal was to ensure source records would not silently disappear during fact loading.

---

## 33. Missing Date Investigation

The 500,000-row taxi sample initially had six records without a matching date dimension record.

Investigation showed:

```text
missing_date = 2025-12-31
trip_count   = 6
```

The date was added to `dim_date`.

After correction:

```text
unmatched_dates = 0
```

This demonstrates why data-quality checks should happen before loading facts.

---

## 34. Idempotency

A rerunnable load should avoid unintended duplicates.

Example:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM fact_orders f
    WHERE f.order_id = o.order_id
)
```

Other protections include:

- Unique constraints
- UPSERT
- MERGE

## 36. Week 4 Key Takeaways

- Define the grain before designing the fact table.
- Facts represent measurable business events.
- Dimensions provide descriptive context.
- IDs are not automatically measures.
- Surrogate keys are warehouse-controlled identifiers.
- Business keys come from source systems.
- Foreign keys connect facts to dimensions.
- Star schemas simplify analytical queries.
- Role-playing dimensions can represent multiple roles.
- Conformed dimensions are shared across business processes.
- SCD Type 1 overwrites history.
- SCD Type 2 preserves history.
- Historical facts should reference the correct historical dimension version.
- Dimension coverage should be validated before loading facts.
- Data-quality issues should be investigated rather than silently discarded.
